Documentação de instalação

LocalGRC

Guia rápido de instalação, utilização e resolução de problemas numa máquina Windows nova.

Versão do guia: 1.0  |  Plataforma de referência: Windows 10/11 + Docker Desktop

1. O que é necessário instalar?

O LocalGRC utiliza Docker Compose para executar os vários componentes da aplicação de forma integrada. Numa instalação normal, não é necessário instalar individualmente o Django, PostgreSQL ou Nginx no Windows.

1.1. Requisitos da máquina

ComponenteRequisito
Sistema operativoWindows 10 ou Windows 11, 64 bits
VirtualizaçãoVirtualização de hardware ativa na BIOS/UEFI
DockerDocker Desktop
Backend de containersWSL 2
MemóriaRecomendados 16 GB, especialmente quando se utiliza Ollama
ArmazenamentoEspaço livre para imagens Docker, base de dados, ficheiros e modelos de IA
RedeAcesso à porta HTTP configurada

1.2. Software necessário

Docker Desktop — descarregar em docker.com/products/docker-desktop.

  • Instalar com o backend WSL 2.
  • Confirmar que a virtualização está ativa.
  • Abrir o Docker Desktop e aguardar que o motor Docker fique operacional.

Git (opcional) — git-scm.com/downloads. Só é necessário se a distribuição for obtida diretamente através de um repositório Git.

Não é necessário instalar diretamente no Windows Python, Django, PostgreSQL, Nginx ou Ollama. Estes componentes são executados ou geridos através dos containers Docker da aplicação.

2. Preparar a instalação

  1. Obter a versão autorizada do código-fonte LocalGRC.
  2. Copiar ou extrair a pasta completa para a máquina de destino.
  3. Confirmar que a pasta contém o docker-compose.yml e as pastas de aplicação e configuração, incluindo backend/ e deploy/.
  4. Confirmar que o Docker Desktop está iniciado.

Abrir o PowerShell e entrar na pasta do projeto. Exemplo (adaptar o caminho):

cd "C:\LocalGRC"

2.1. Confirmar o Docker

docker --version
docker compose version
docker info

Os comandos devem devolver informação de versão e estado. Se docker info falhar, confirmar que o Docker Desktop está aberto e que o motor terminou o arranque.

3. Configuração inicial

Antes do primeiro arranque, confirmar a configuração fornecida com a distribuição do LocalGRC.

  • Porta HTTP a utilizar.
  • Credenciais iniciais da conta administradora e procedimento de definição da palavra-passe.
  • Chave secreta Django.
  • Credenciais de acesso à base de dados.
  • Configuração dos modelos Ollama, quando aplicável.
  • Origens e endereços autorizados pela aplicação, quando aplicável.
Segurança — configurar credenciais próprias Não reutilizar palavras-passe de demonstração. Utilizar uma palavra-passe administrativa forte e exclusiva. Não publicar ficheiros de configuração com segredos no Git, nem expor diretamente as portas internas da base de dados ou do Ollama à Internet.

A configuração atual do projeto define 8081 como porta HTTP predefinida no Compose atualizado. Uma variável HTTP_PORT definida no ambiente ou no ficheiro de configuração pode substituir esse valor. Confirmar sempre a porta efetivamente publicada com docker compose ps.

4. Primeiro arranque da aplicação

No PowerShell, dentro da pasta do projeto, executar:

docker compose up -d --build

O comando constrói as imagens necessárias, cria os containers e inicia os serviços em segundo plano. O primeiro arranque pode demorar mais tempo devido à transferência de imagens e à preparação dos componentes.

4.1. Confirmar os serviços

docker compose ps -a
ServiçoFunção
appBackend Django
dbBase de dados PostgreSQL
webNginx e acesso HTTP
ollamaServiço de modelos de IA
backupServiço de cópias de segurança

O PostgreSQL deverá apresentar o estado healthy. Os restantes serviços deverão estar em execução (Up).

4.2. Abrir a aplicação

Utilizar a porta configurada. Exemplos:

http://localhost:8081
http://localhost:8080

O endereço correto depende da configuração da instalação. Deverá surgir o ecrã de autenticação.

5. Primeiro acesso

Utilizar as credenciais administrativas definidas durante o provisionamento da instalação. O endereço de e-mail e a palavra-passe devem corresponder à conta efetivamente criada.

Depois de entrar:

  1. Confirmar que o Dashboard abre corretamente.
  2. Verificar a organização inicial.
  3. Confirmar os módulos disponíveis.
  4. Criar ou configurar os utilizadores necessários.
  5. Atribuir os perfis e permissões adequados.
  6. Rever as configurações da organização.

Não utilizar uma conta administrativa para o trabalho diário de utilizadores com funções limitadas.

5.1. Redefinir a palavra-passe de uma conta

Se a conta administrativa tiver o endereço admin@local, o Django permite solicitar uma nova palavra-passe através de:

docker compose exec app python manage.py changepassword admin@local

O endereço de e-mail deve ser ajustado caso a conta administrativa tenha outro identificador.

6. Utilização diária

6.1. Iniciar a aplicação

cd "C:\LocalGRC"
docker compose up -d

6.2. Confirmar o estado

docker compose ps

6.3. Reiniciar os serviços

docker compose restart

6.4. Parar a aplicação

docker compose stop

O comando stop pára os containers, mas mantém os dados persistentes. Para voltar a iniciar:

docker compose up -d
Não eliminar volumes Não utilizar docker compose down -v como procedimento normal de paragem ou manutenção. A opção -v pode eliminar volumes que contêm a base de dados e outros dados persistentes.

7. Resolução de problemas (Troubleshooting)

7.1. Docker não inicia

Sintoma: os comandos Docker devolvem erros de ligação.

  1. Confirmar que o Docker Desktop está aberto.
  2. Aguardar que o motor Docker fique operacional.
  3. Confirmar que a virtualização está ativa.
  4. Verificar o estado do WSL 2.
docker info
wsl --status

7.2. A aplicação não abre no navegador

Sintoma: localhost não responde.

Confirmar os containers e a porta publicada:

docker compose ps -a
docker compose ps web

Testar o acesso HTTP, substituindo 8081 pela porta efetivamente configurada:

curl.exe -I http://localhost:8081

Uma resposta HTTP 200 ou 302 indica que existe comunicação com o serviço Web. Um redirecionamento 302 para /login/ é normal quando não existe uma sessão autenticada.

7.3. Erro de porta já utilizada

Sintoma:

Bind for 0.0.0.0:8080 failed: port is already allocated

Outro programa ou container já está a utilizar a porta. Identificar os containers e respetivas portas:

docker ps --format "table {{.Names}}\t{{.Ports}}"

Escolher uma porta livre e ajustar HTTP_PORT ou a configuração correspondente. Não parar outras instalações sem confirmar a que aplicação pertencem.

7.4. Nginx apresenta erro de upstream app

Sintoma:

host not found in upstream "app"

O Nginx não está a conseguir resolver o nome do serviço Django na rede Docker. Consultar os logs:

docker compose logs web --tail 100
docker compose ps app

Se o container Nginx estiver em execução, testar a resolução DNS:

docker exec localgrc-base-web-1 getent hosts app

Se a resolução falhar, e depois de confirmar que o serviço app está ativo, recriar apenas o Nginx através do Compose:

docker compose up -d --no-deps --force-recreate web

Voltar a testar a resolução do nome app e o acesso HTTP. Não utilizar endereços IP fixos na configuração Nginx: os endereços internos dos containers podem mudar.

7.5. Erro HTTP 500 depois do login

Consultar os logs do backend e do Nginx:

docker compose logs app --tail 200
docker compose logs web --tail 100

Registar o módulo onde ocorreu o erro, a hora aproximada, a operação efetuada e a mensagem apresentada nos logs. Não apagar a base de dados nem executar migrações manualmente sem identificar a causa.

7.6. Base de dados indisponível

docker compose ps db
docker compose logs db --tail 100

Aguardar que o PostgreSQL apresente healthy. Não eliminar o volume pgdata como tentativa de resolução.

7.7. Serviço Ollama indisponível

docker compose ps ollama
docker compose logs ollama --tail 100

A indisponibilidade do serviço de IA pode afetar funcionalidades dependentes dos modelos, sem significar necessariamente que o restante LocalGRC esteja indisponível.

8. Cópias de segurança e proteção dos dados

A instalação utiliza volumes Docker persistentes, incluindo:

VolumeConteúdo
pgdataDados PostgreSQL
uploadsFicheiros carregados
staticfilesFicheiros estáticos
ollama_modelsModelos Ollama

Confirmar que o serviço de backup está ativo e consultar os respetivos logs:

docker compose ps backup
docker compose logs backup --tail 100

O administrador deve confirmar periodicamente que as cópias são produzidas, onde são armazenadas, que existe espaço disponível e que podem ser recuperadas.

Recomendação Manter cópias externas à máquina onde a aplicação está instalada. Uma cópia guardada apenas no mesmo disco não protege contra a falha desse disco. Confirmar o destino e a política de retenção efetivamente configurados na distribuição.

9. Atualização da aplicação

Antes de atualizar:

  1. Confirmar que existe uma cópia de segurança válida.
  2. Obter a versão autorizada do projeto.
  3. Consultar as notas da versão.
  4. Aplicar a atualização de acordo com os procedimentos definidos para essa versão.

Quando existirem alterações ao código, Dockerfile ou dependências, reconstruir:

docker compose up -d --build

Confirmar depois:

docker compose ps -a

Não eliminar volumes nem apagar dados para efetuar uma atualização.

10. Checklist de validação da instalação

  • Docker Desktop instalado e operacional.
  • WSL 2 funcional.
  • Código-fonte completo e configuração validada.
  • Credenciais e segredos próprios da instalação.
  • Containers iniciados.
  • PostgreSQL com estado healthy.
  • Nginx acessível na porta configurada.
  • Ecrã de autenticação apresentado.
  • Login administrativo testado.
  • Dashboard e módulos principais testados.
  • Serviço de IA validado, quando aplicável.
  • Serviço de backup ativo e cópias verificadas.
  • Procedimento de recuperação conhecido.
Instalação concluída A instalação só deverá ser considerada concluída depois de validar o acesso, a autenticação, os módulos principais e a existência de cópias de segurança recuperáveis.
